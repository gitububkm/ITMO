# Аналитическое исследование практик безопасной разработки

**Дисциплина:** DevOps and DevSecOps  
**Работа №1:** Аналитическое исследование практик безопасной разработки  
**Формат:** аналитический отчёт

---

## Введение

Безопасная разработка программного обеспечения (Secure Software Development) предполагает встраивание мер защиты не в конце жизненного цикла, а на всех его этапах — от планирования до эксплуатации. Такой подход лежит в основе концепции **DevSecOps** и принципа **Shift Left**: чем раньше обнаружена уязвимость или архитектурный риск, тем дешевле и проще его устранить.

Цель данной работы — провести аналитическое исследование практик безопасной разработки: выбрать набор ключевых практик, разобрать каждую по единой схеме и сопоставить практики с этапами жизненного цикла программного обеспечения (ЖЦ ПО).

**Задачи исследования:**
1. Выбрать 10 практик безопасной разработки, актуальных для современных процессов поставки ПО.
2. Для каждой практики определить: назначение, предотвращаемые/обнаруживаемые проблемы, этап ЖЦ ПО, способ реализации, преимущества, недостатки и пример инструмента.
3. Структурировать этапы разработки ПО и связать с ними рассмотренные практики.
4. Сформулировать аналитические выводы о том, как практики дополняют друг друга в контуре DevSecOps.

**Объект исследования** — практики и инструменты безопасной разработки.  
**Предмет исследования** — их роль, место в ЖЦ ПО и практическая применимость в CI/CD.

В работе рассмотрены следующие практики:
1. Threat Modeling (моделирование угроз);
2. Secure Code Review (безопасный code review);
3. SAST (Static Application Security Testing);
4. Secret Scanning;
5. SCA / Dependency Scanning и SBOM;
6. Container / Image Security Scanning;
7. DAST (Dynamic Application Security Testing);
8. IAST / Runtime Instrumentation (смежно — RASP);
9. Vulnerability Management и triage (Defect Management);
10. Infrastructure as Code Security / Policy as Code.

## 1. Обзор практик безопасной разработки

В данном разделе для каждой выбранной практики приведены ответы на все требуемые пункты анализа:
1) название;  
2) назначение;  
3) предотвращаемые или обнаруживаемые проблемы и уязвимости;  
4) этап жизненного цикла ПО;  
5) способ практической реализации;  
6) основные преимущества;  
7) возможные недостатки и ограничения;  
8) пример инструмента, технологии или способа реализации.

### 1.1. Threat Modeling (моделирование угроз)

#### 1.1.1. Название практики
Threat Modeling — систематическое моделирование угроз, активов и сценариев атак.

#### 1.1.2. Назначение
Практика используется для раннего выявления рисков безопасности ещё до активной разработки или при существенном изменении архитектуры. Она помогает понять, *что* нужно защищать, *от кого*, *какими способами* система может быть атакована и какие контрмеры приоритетны.

#### 1.1.3. Проблемы и уязвимости, которые позволяет предотвратить или обнаружить
- неучтённые бизнес-риски и «слепые зоны» в требованиях безопасности;
- слабая или неполная модель аутентификации и авторизации;
- отсутствие защиты критичных потоков данных (персональные данные, платежи, секреты);
- ошибки в границах доверия между сервисами (trust boundaries);
- архитектурные решения, которые позже почти невозможно «закрыть» точечными патчами.

#### 1.1.4. Этап жизненного цикла ПО
Планирование и проектирование; повторно — при крупных изменениях архитектуры, появлении новых интеграций или изменении модели угроз.

#### 1.1.5. Как практика реализуется
Проводятся сессии с участием архитекторов, разработчиков и специалистов по безопасности. Строятся диаграммы потоков данных (DFD), применяются методологии STRIDE, PASTA, LINDDUN или аналоги. Угрозы фиксируются, оцениваются по вероятности/воздействию, контрмеры заводятся в бэклог как security requirements и задачи.

#### 1.1.6. Основные преимущества
- снижает стоимость исправлений за счёт раннего обнаружения рисков;
- формирует общее понимание угроз у команды;
- позволяет приоритизировать защитные меры, а не внедрять «всё подряд»;
- даёт контекст для последующих сканеров (что именно критично проверять).

#### 1.1.7. Недостатки и ограничения
- требует времени и экспертизы;
- результаты устаревают без регулярного пересмотра;
- оценка рисков частично субъективна;
- без связи с бэклогом и CI практика превращается в «документ ради документа».

#### 1.1.8. Пример инструмента или технологии
Microsoft Threat Modeling Tool, OWASP Threat Dragon, IriusRisk; методологии STRIDE и PASTA.

### 1.2. Secure Code Review (безопасный code review)

#### 1.2.1. Название практики
Secure Code Review — проверка изменений кода на уязвимости и соответствие стандартам безопасного кодирования.

#### 1.2.2. Назначение
Практика нужна для того, чтобы до попадания кода в основную ветку выявить логические и контекстные ошибки безопасности, которые плохо ловятся автоматическими сканерами: ошибки авторизации, неверная валидация входных данных, опасные паттерны работы с данными.

#### 1.2.3. Проблемы и уязвимости, которые позволяет предотвратить или обнаружить
- injection-уязвимости (SQL Injection, XSS, OS Command Injection);
- небезопасная десериализация;
- Broken Access Control / ошибки проверки прав;
- утечки секретов и чувствительных данных в коде и логах;
- слабая или самописная криптография;
- нарушения внутренних secure coding guidelines.

#### 1.2.4. Этап жизненного цикла ПО
Разработка; непосредственно перед merge (Merge Request / Pull Request).

#### 1.2.5. Как практика реализуется
Вводятся обязательные правила review (минимум один approve), чеклисты по OWASP/внутренним стандартам, назначение Code Owners для критичных модулей, обучение команды. Review дополняется автоматическими проверками (SAST, linters), но не заменяется ими.

#### 1.2.6. Основные преимущества
- хорошо ловит контекстные и бизнес-логические проблемы;
- повышает культуру качества и обмена знаниями;
- снижает вероятность регрессий по безопасности в критичных местах.

#### 1.2.7. Недостатки и ограничения
- качество зависит от квалификации ревьюера;
- при больших диффах замедляет поставку;
- плохо масштабируется без автоматизации и чётких чеклистов;
- усталость ревьюеров приводит к формальному «approve».

#### 1.2.8. Пример инструмента или технологии
GitLab Merge Request approvals, GitHub Code Owners и branch protection rules, Bitbucket Reviewers; методическое основание — OWASP Code Review Guide.

### 1.3. SAST (Static Application Security Testing)

#### 1.3.1. Название практики
SAST — статическое тестирование безопасности приложений (анализ исходного кода без выполнения программы).

#### 1.3.2. Назначение
Автоматически находить потенциальные уязвимости и опасные конструкции в коде на ранних этапах, в том числе в CI/CD, чтобы реализовать принцип Shift Left.

#### 1.3.3. Проблемы и уязвимости, которые позволяет предотвратить или обнаружить
- XSS, SQL Injection, path traversal;
- использование небезопасных API и функций;
- часть проблем с валидацией входных данных;
- hard-coded secrets (частично, в зависимости от правил);
- некоторые ошибки управления ресурсами и обработкой ошибок, влияющие на безопасность.

#### 1.3.4. Этап жизненного цикла ПО
Разработка и непрерывная интеграция (CI), этап сборки/проверки изменений.

#### 1.3.5. Как практика реализуется
Сканер подключается к pipeline: анализ на каждый commit или Merge Request, публикация отчёта, quality gate (например, fail при Critical/High). Команда настраивает правила под стек, ведёт triage ложных срабатываний и исключений.

#### 1.3.6. Основные преимущества
- раннее обнаружение дефектов;
- высокая повторяемость и масштабируемость;
- относительно быстрая обратная связь разработчику;
- хорошо встраивается в GitLab/GitHub CI.

#### 1.3.7. Недостатки и ограничения
- ложные срабатывания (false positives);
- ограниченное понимание runtime-контекста и реальной эксплуатируемости;
- требует калибровки правил под проект;
- не заменяет DAST и ручной анализ бизнес-логики.

#### 1.3.8. Пример инструмента или технологии
Semgrep, SonarQube, GitLab SAST, CodeQL, Checkmarx.

### 1.4. Secret Scanning

#### 1.4.1. Название практики
Secret Scanning — поиск секретов в коде, конфигурациях, артефактах и истории Git.

#### 1.4.2. Назначение
Не допустить утечки ключей, токенов, паролей и сертификатов в репозиторий и предотвратить их повторное появление; при обнаружении — инициировать ротацию и очистку.

#### 1.4.3. Проблемы и уязвимости, которые позволяет предотвратить или обнаружить
- коммит API-ключей, паролей БД, private keys, CI/CD tokens;
- секреты в `.env`, конфигах, скриптах и Docker-слоях;
- компрометация облачных и внешних сервисов из-за публичного или доступного репозитория;
- «забытые» секреты в старых коммитах истории Git.

#### 1.4.4. Этап жизненного цикла ПО
Разработка (pre-commit), CI на каждый MR, периодический аудит полной истории; также контроль на этапе сборки артефактов.

#### 1.4.5. Как практика реализуется
Устанавливаются pre-commit hooks, CI-джобы secret detection, политики блокировки merge при находках. Секреты хранятся в менеджерах секретов (Vault и аналоги). При утечке выполняется ротация и очистка истории (`git filter-repo`, BFG).

#### 1.4.6. Основные преимущества
- быстро снижает риск массовых компрометаций;
- легко автоматизируется;
- даёт понятный и измеримый контроль «секреты не в Git».

#### 1.4.7. Недостатки и ограничения
- не заменяет правильное управление секретами и least privilege;
- возможны обходы (кодирование, разбиение строк);
- уже попавшие в историю секреты требуют отдельной процедуры очистки и ротации;
- возможны ложные срабатывания на тестовые/fake-значения.

#### 1.4.8. Пример инструмента или технологии
Gitleaks, TruffleHog, GitLab Secret Detection; для очистки истории — `git-filter-repo`, BFG Repo-Cleaner; для хранения — HashiCorp Vault, GitLab/GitHub protected variables.

### 1.5. SCA / Dependency Scanning и SBOM

#### 1.5.1. Название практики
SCA (Software Composition Analysis) / Dependency Scanning совместно с генерацией SBOM (Software Bill of Materials).

#### 1.5.2. Назначение
Контролировать безопасность и лицензионную чистоту сторонних компонентов; фиксировать состав программного продукта для прозрачности supply chain и быстрого реагирования на новые CVE.

#### 1.5.3. Проблемы и уязвимости, которые позволяет предотвратить или обнаружить
- известные CVE в прямых и транзитивных зависимостях (пример класса риска — Log4Shell);
- использование устаревших и неподдерживаемых библиотек;
- supply chain риски (компрометация пакетов);
- нарушение лицензионной политики организации.

#### 1.5.4. Этап жизненного цикла ПО
Сборка (build) и CI; далее — сопровождение уже выпущенных версий при появлении новых уязвимостей.

#### 1.5.5. Как практика реализуется
В pipeline анализируются lock-файлы и манифесты зависимостей, генерируется SBOM (CycloneDX/SPDX), задаются политики по severity и лицензиям, настраивается процесс обновления зависимостей и пересборки. SBOM сохраняется как артефакт релиза.

#### 1.5.6. Основные преимущества
- закрывает значительную долю внешних рисков современного ПО;
- повышает прозрачность состава продукта;
- ускоряет реакцию на массовые уязвимости («затронуты ли мы?»);
- хорошо автоматизируется.

#### 1.5.7. Недостатки и ограничения
- шум из-за транзитивных и фактически недостижимых CVE;
- ложные positives и необходимость triage;
- сам факт наличия CVE не всегда означает эксплуатируемость в конкретном контексте;
- нужен устойчивый процесс патчинга, иначе отчёты бесполезны.

#### 1.5.8. Пример инструмента или технологии
OWASP Dependency-Check, Snyk, Trivy, Grype, Syft; форматы SBOM — CycloneDX, SPDX; в контексте курса также упоминается Butesafe.

### 1.6. Container / Image Security Scanning

#### 1.6.1. Название практики
Сканирование контейнерных образов (Container / Image Security Scanning).

#### 1.6.2. Назначение
Проверять безопасность артефактов поставки в контейнерной среде: уязвимости пакетов ОС и приложений в образе, а также отдельные классы misconfiguration.

#### 1.6.3. Проблемы и уязвимости, которые позволяет предотвратить или обнаружить
- устаревшие и уязвимые базовые образы;
- CVE в системных пакетах внутри image;
- наличие лишних инструментов/пакетов, увеличивающих поверхность атаки;
- запуск от root, избыточные привилегии, секреты, «зашитые» в слои образа.

#### 1.6.4. Этап жизненного цикла ПО
Сборка образов, публикация в registry, этап CD перед выкатом; политика admission в кластере.

#### 1.6.5. Как практика реализуется
Скан запускается после `docker build` / в CI и при push в registry. Вводятся quality gates и admission-политики (запрет деплоя уязвимых или non-compliant образов). Используются минимальные base images (distroless/alpine) и multi-stage builds.

#### 1.6.6. Основные преимущества
- соответствует современной контейнерной модели поставки;
- контролирует конечный артефакт, а не только исходники;
- легко встраивается в GitLab CI и registry workflow.

#### 1.6.7. Недостатки и ограничения
- зависит от полноты и актуальности баз CVE;
- не гарантирует безопасность runtime-конфигурации Kubernetes/облака;
- без минимализации образов отчёты становятся шумными;
- требует политики: что блокируем, что принимаем как risk acceptance.

#### 1.6.8. Пример инструмента или технологии
Trivy, Grype, Clair, Harbor Vulnerability Scanner, Docker Scout.

### 1.7. DAST (Dynamic Application Security Testing)

#### 1.7.1. Название практики
DAST — динамическое тестирование безопасности приложений (анализ работающего приложения «снаружи»).

#### 1.7.2. Назначение
Обнаруживать уязвимости и misconfiguration, проявляющиеся только в runtime, путём имитации атак на развёрнутый стенд или окружение.

#### 1.7.3. Проблемы и уязвимости, которые позволяет предотвратить или обнаружить
- XSS/SQLi и другие injection на живом приложении;
- небезопасные HTTP-заголовки и cookie-флаги;
- открытые административные или отладочные эндпоинты;
- проблемы сессий и аутентификации, видимые извне;
- часть ошибок авторизации на реальных API-маршрутах.

#### 1.7.4. Этап жизненного цикла ПО
Тестирование и staging; после развёртывания тестового/предпродового окружения. Иногда — контролируемые проверки на production-like стендах.

#### 1.7.5. Как практика реализуется
Приложение разворачивается на стенде, поднимается сканер (часто в CI после deploy to staging), выполняются аутентифицированные и неаутентифицированные проверки, отчёт разбирается, подтверждённые дефекты заводятся в трекер.

#### 1.7.6. Основные преимущества
- ближе к реальной модели атаки;
- находит то, что не видно статическим анализом;
- проверяет связку приложения, конфигурации и окружения.

#### 1.7.7. Недостатки и ограничения
- нужен доступный стенд и корректные тестовые данные;
- дольше и ресурсоёмче SAST;
- хуже покрывает глубокую бизнес-логику без сценариев и карты приложения;
- риск воздействия на окружение при агрессивных проверках.

#### 1.7.8. Пример инструмента или технологии
OWASP ZAP, Burp Suite, GitLab DAST, Nuclei.

### 1.8. IAST / Runtime Instrumentation (смежно — RASP)

#### 1.8.1. Название практики
IAST (Interactive Application Security Testing) — интерактивный анализ за счёт инструментирования приложения во время его работы; смежная практика — RASP (Runtime Application Self-Protection).

#### 1.8.2. Назначение
Совместить выполнение выполнения приложения (тесты, реальный трафик) с наблюдением внутри runtime, чтобы точнее выявлять уязвимости и, в случае RASP, блокировать атаки в момент эксплуатации.

#### 1.8.3. Проблемы и уязвимости, которые позволяет предотвратить или обнаружить
- уязвимости на реально исполняемых путях кода;
- подтверждение эксплуатируемости находок SAST;
- injection и доступ к данным в контексте фактических запросов;
- (для RASP) попытки атак в runtime с возможностью блокировки/алерта.

#### 1.8.4. Этап жизненного цикла ПО
Этап тестирования (QA) для IAST; для RASP — преимущественно эксплуатация (production/pre-prod).

#### 1.8.5. Как практика реализуется
В приложение внедряется агент/инструментация. Во время автотестов или на стенде агент коррелирует входящие запросы с участками кода и формирует findings. Для RASP задаются политики реагирования (detect/block).

#### 1.8.6. Основные преимущества
- обычно меньше false positives, чем у «чистого» SAST;
- высокая полезность за счёт привязки к реальному выполнению;
- ускоряет валидацию, эксплуатируема ли проблема.

#### 1.8.7. Недостатки и ограничения
- нужен агент и интеграция в runtime;
- зрелость и поддержка зависят от языка/платформы;
- возможны overhead по производительности;
- стоимость коммерческих решений может быть высокой.

#### 1.8.8. Пример инструмента или технологии
Contrast Security, Seeker (Synopsys), OpenRASP; концептуально — agent-based runtime security.

### 1.9. Vulnerability Management и triage (Defect Management)

#### 1.9.1. Название практики
Vulnerability Management / Defect Management — централизованное управление уязвимостями: сбор, triage, валидация, приоритизация и контроль исправления.

#### 1.9.2. Назначение
Превратить поток находок из SAST, DAST, SCA, image scanning и ручных проверок в управляемый процесс: отличать истинные дефекты от ложных, назначать владельцев, соблюдать SLA и измерять эффективность исправлений.

#### 1.9.3. Проблемы и уязвимости, которые позволяет предотвратить или обнаружить
Практика сама по себе не «ищет» новые классы багов, но предотвращает организационные провалы:
- потерю Critical/High в шуме отчётов;
- дублирование одних и тех же findings из разных сканеров;
- отсутствие ответственности и сроков исправления;
- повторное появление уже закрытых уязвимостей;
- неконтролируемый technical security debt.

#### 1.9.4. Этап жизненного цикла ПО
Все этапы после появления findings; особенно тестирование, релиз и сопровождение. Фактически — сквозная практика DevSecOps.

#### 1.9.5. Как практика реализуется
Разворачивается Defect Tracker (например, DefectDojo), настраивается импорт отчётов сканеров, процесс triage (True Positive / False Positive / Accept Risk), интеграция с Jira/GitLab Issues, метрики MTTR, SLA по severity, регулярные triage-сессии.

#### 1.9.6. Основные преимущества
- делает безопасность управляемой и измеримой;
- снижает хаос от множества инструментов;
- повышает качество решений «что чинить сначала»;
- связывает Dev, Sec и Ops вокруг единого backlog дефектов.

#### 1.9.7. Недостатки и ограничения
- без дисциплины triage инструмент становится «свалкой алертов»;
- требует интеграций и поддержки процесса;
- нужен выделенный ownership (AppSec/DevSecOps роль);
- на старте возможны высокие трудозатраты на разбор накопленного шума.

#### 1.9.8. Пример инструмента или технологии
DefectDojo, Faraday, Hexway Hive; связка с Jira / GitLab Issues как issue-tracker.

### 1.10. Infrastructure as Code Security / Policy as Code

#### 1.10.1. Название практики
IaC Security и Policy as Code — проверка инфраструктурного кода и политик безопасности до применения изменений в облаке или кластере.

#### 1.10.2. Назначение
Предотвращать опасные конфигурации инфраструктуры на этапе описания инфраструктуры кодом, а также автоматически enforcing политики при deploy.

#### 1.10.3. Проблемы и уязвимости, которые позволяет предотвратить или обнаружить
- публично доступные хранилища и нагрузки;
- открытые security groups / слишком широкие firewall-правила;
- слабые IAM-роли и избыточные привилегии;
- privileged Pod, отсутствие resource limits, отсутствие network policy в Kubernetes;
- небезопасные значения по умолчанию в Terraform/Helm/манифестах.

#### 1.10.4. Этап жизненного цикла ПО
Проектирование и подготовка инфраструктуры; CI перед `terraform apply` / deploy; runtime-enforcement через admission controllers.

#### 1.10.5. Как практика реализуется
В pipeline добавляется сканирование Terraform, Helm, Kubernetes YAML; политики описываются как код (OPA/Conftest, Kyverno). Нарушения блокируют merge или apply. В кластере работают admission policies.

#### 1.10.6. Основные преимущества
- предотвращает misconfiguration до попадания в production;
- политики версионируются и ревьюятся как код;
- хорошо масштабируется на многие команды и репозитории.

#### 1.10.7. Недостатки и ограничения
- политики нужно проектировать и поддерживать;
- не покрывает configuration drift, если инфраструктуру меняют вручную вне IaC;
- возможны ложные блокировки при слишком жёстких правилах;
- требует зрелости IaC-практик в команде.

#### 1.10.8. Пример инструмента или технологии
Checkov, tfsec, Terrascan, OPA/Gatekeeper, Kyverno, Conftest.

## 3. Этапы жизненного цикла ПО и связанные практики

В этом разделе структурированы основные этапы ЖЦ ПО и показано, какие из рассмотренных практик к ним относятся. Это аналитическая часть, требуемая заданием: не просто перечень практик, а их привязка к процессу разработки и поставки.

### 3.1. Планирование и формирование требований

**Цель этапа:** понять ценность продукта, ограничения, риски и критерии приёмки.

**Связанные практики:**
- Threat Modeling — формирование security requirements и карты рисков;
- элементы Vulnerability Management — определение SLA и severity-политик «на берегу».

**Аналитический комментарий:**  
Если на этом этапе не зафиксированы ожидания по безопасности, последующие сканеры дают находки без приоритета и бизнес-контекста. Threat Modeling здесь — основа для осмысленного DevSecOps, а не «галочка».

### 3.2. Проектирование и архитектура

**Цель этапа:** выбрать архитектуру, границы доверия, модель идентичности и схему интеграций.

**Связанные практики:**
- Threat Modeling (углублённо: DFD, trust zones, STRIDE);
- IaC Security / Policy as Code — если инфраструктура проектируется сразу как код.

**Аналитический комментарий:**  
Ошибки авторизации между сервисами, публичные интерфейсы и неверная декомпозиция доверия редко полностью компенсируются SAST/DAST. Архитектурная безопасность дешевле любой поздней автоматизации.

### 3.3. Разработка

**Цель этапа:** реализовать функциональность в коде с соблюдением стандартов качества и безопасности.

**Связанные практики:**
- Secure Code Review;
- SAST;
- Secret Scanning (pre-commit и на MR).

**Аналитический комментарий:**  
Оптимальная модель — «автомат + человек»: SAST и secret scan дают быстрый фильтр, review закрывает логику доступа и доменные риски. Исключение любого из элементов ослабляет контур.

### 3.4. Сборка и формирование артефактов

**Цель этапа:** получить воспроизводимый артефакт (бинарник, пакет, контейнерный образ) и зафиксировать его состав.

**Связанные практики:**
- SCA / Dependency Scanning + SBOM;
- Container / Image Security Scanning;
- повторный Secret Scanning конфигов и артефактов.

**Аналитический комментарий:**  
Именно здесь проявляется supply chain security. SBOM нужен не как формальность, а как база для ответа на вопрос: «затронула ли нас новая CVE?». Image scanning проверяет уже итоговый контейнерный артефакт поставки.

### 3.5. Тестирование

**Цель этапа:** подтвердить качество и безопасность на стенде до релиза.

**Связанные практики:**
- DAST;
- IAST (при наличии);
- Vulnerability Management / triage найденных дефектов.

**Аналитический комментарий:**  
Тестирование без triage превращает security в поток PDF-отчётов. DAST/IAST дополняют статику runtime-сигналом, а Defect Management превращает сигнал в задачи с владельцами и сроками.

### 3.6. Развёртывание и релиз

**Цель этапа:** безопасно доставить изменение в целевое окружение.

**Связанные практики:**
- IaC / Policy as Code (включая admission policies);
- quality gates по результатам SAST/SCA/image scan;
- контроль секретов в CI/CD (не в репозитории).

**Аналитический комментарий:**  
Безопасность должна быть условием выката. Если pipeline только «информирует», но не блокирует Critical, практика деградирует до декоративной отчётности.

### 3.7. Эксплуатация и сопровождение

**Цель этапа:** поддерживать безопасное состояние продукта после релиза, реагировать на новые угрозы и инциденты.

**Связанные практики:**
- непрерывный SCA по новым CVE;
- Vulnerability Management со SLA и метриками;
- RASP/мониторинг атак (опционально);
- реагирование на утечки секретов (ротация, очистка истории);
- пересмотр Threat Model при существенных изменениях.

**Аналитический комментарий:**  
DevSecOps — цикл, а не разовый скан перед релизом. Сопровождение без повторной оценки зависимостей и без процесса исправления быстро обесценивает все shift-left усилия.

### 3.8. Сквозная схема соответствия «этап → практики»

| Этап ЖЦ ПО | Практики |
|------------|----------|
| Планирование / требования | Threat Modeling; политики Vulnerability Management |
| Проектирование | Threat Modeling; IaC / Policy as Code |
| Разработка | Secure Code Review; SAST; Secret Scanning |
| Сборка | SCA + SBOM; Image Scanning; Secret Scanning |
| Тестирование | DAST; IAST; triage в Defect Management |
| Развёртывание | Policy as Code; quality gates; безопасное управление секретами CI/CD |
| Эксплуатация | SCA continuous; Defect Management; RASP/мониторинг; реакция на секреты; обновление Threat Model |

## 4. Сравнительный анализ и практические выводы

### 4.1. Как практики дополняют друг друга

Ни одна практика не закрывает весь риск самостоятельно:
- **SAST** видит код, но слабо понимает runtime;
- **DAST** видит runtime, но хуже локализует причину в коде;
- **SCA** закрывает зависимости, но не бизнес-логику;
- **Secret Scanning** критичен, но узкоспециализирован;
- **Threat Modeling** даёт смысл и приоритеты, но не заменяет технические проверки;
- **Defect Management** не ищет уязвимости, но без него остальные практики теряют управляемость.

Следовательно, ценность возникает из **комбинации** практик в едином контуре.

### 4.2. Принцип Shift Left и его границы

Перенос проверок влево (review, SAST, secrets, SCA на ранних стадиях) уменьшает стоимость исправления. Однако без правой части контура — DAST, admission policies, сопровождение CVE — остаются риски окружения, конфигурации и пост-релизных уязвимостей. Зрелый процесс сочетает оба направления.

### 4.3. Роль автоматизации и человеческого фактора

Автоматизация масштабирует обнаружение, но:
- triage всё равно требует экспертизы;
- secure code review остаётся необходимым для authZ и доменной логики;
- политики quality gate должны быть согласованы с командой, иначе их будут обходить.

### 4.4. Рекомендуемый минимальный контур для учебного/боевого DevSecOps

С учётом логики последующих работ дисциплины целесообразен такой базовый контур:

1. GitLab как платформа разработки и CI/CD;  
2. SAST в pipeline;  
3. DefectDojo для triage и учёта;  
4. автоматизация тестов сборки;  
5. Secret Scanning (+ очистка истории при инциденте);  
6. SBOM + Dependency Scanning;  
7. DAST на развёрнутом стенде и разбор находок.

Такой порядок отражает переход от организационно-аналитической зрелости к конкретным техническим контрольным точкам.

## Заключение

В ходе аналитического исследования рассмотрены **10 практик безопасной разработки**. Для каждой практики определены назначение, круг предотвращаемых или обнаруживаемых проблем, этап жизненного цикла ПО, способ реализации, преимущества, ограничения и пример инструмента — в полном соответствии с требованиями задания.

Дополнительно построена структура этапов ЖЦ ПО (планирование, проектирование, разработка, сборка, тестирование, развёртывание, эксплуатация) и показано, какие практики на каком этапе применяются. Это позволяет рассматривать безопасность не как набор разрозненных сканеров, а как сквозной процесс.

Ключевые выводы:
1. Эффективный DevSecOps строится на комбинации практик, а не на одном инструменте.
2. Ранние практики (Threat Modeling, Secure Review, SAST, Secret Scanning) снижают стоимость дефектов.
3. Практики сборки и поставки (SCA/SBOM, Image Scanning, Policy as Code) закрывают supply chain и конфигурационные риски.
4. Runtime-проверки (DAST/IAST) и последующий triage обязательны для подтверждения и управления реальным риском.
5. Без Vulnerability Management даже сильный набор сканеров не превращается в управляемую безопасность продукта.

Таким образом, цель работы достигнута: выполнен сравнительный разбор практик безопасной разработки и сформирована аналитическая модель их распределения по жизненному циклу программного обеспечения.
